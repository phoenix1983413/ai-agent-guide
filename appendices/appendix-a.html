主流框架横向对比

LangChain / LlamaIndex / CrewAI / AutoGen / Semantic Kernel / Dify / 自研

选择 Agent 框架时没有「银弹」，只有「最适合你当前阶段的工具」。选型前先明确三件事：团队语言栈（.NET 团队强上 Python 生态是折磨）、Agent 复杂度（L1 工具调用不需要编排框架）、数据主权要求（是否必须私有化部署）。以下从六个维度对比主流框架：

框架语言核心定位学习曲线社区活跃度优点缺点适用场景
LangChainPython / TS通用 LLM 应用框架中高生态全、工具多、文档完善抽象层重、debug 链路长快速原型、工具链复杂
LlamaIndexPythonRAG / 数据索引中高数据连接器丰富、检索调优灵活Agent 编排弱于 LangChain知识库问答、文档 Agent
CrewAIPython多 Agent 协作低中高角色定义简单、开箱即用灵活性有限、深度定制难多 Agent 编排、快速验证
AutoGenPython多 Agent 对话中中微软背书、对话流自然版本迭代快、API 不稳定研究原型、对话式 Agent
Semantic KernelC# / Python企业级 AI 编排中高中微软生态、企业集成强非主流语言、社区较小.NET 团队、企业 Azure
DifyPython + Web UI低代码 LLM 应用平台低中高可视化编排、内置 RAG、一键部署深度定制受限、调试黑盒业务团队自助、内部工具
Google ADKPythonGoogle 系 Agent 开发套件中中原生 A2A 支持、评测工具全绑定 Google 生态Gemini 技术栈团队
自研任意完全可控高—无依赖、性能与可控性最优开发成本高、维护负担重特殊需求、强工程团队

选型决策树

  1. 必须私有化部署 / 数据不出域？ → 是 → 优先自研或 Dify 本地版；否 → 继续。
  2. 团队主力语言是 .NET？ → 是 → Semantic Kernel；否 → 继续。
  3. 核心需求是 RAG 知识库？ → 是 → LlamaIndex 为主 + LangChain 补编排；否 → 继续。
  4. 核心需求是多 Agent 协作？ → 是 → CrewAI（快）/ AutoGen（灵活）；否 → 继续。
  5. 业务团队要自己搭？ → 是 → Dify / Coze；否 → 继续。
  6. 默认答案 → LangChain（Python 团队）或 自研薄封装（强工程团队）。

防绑定的工程纪律

框架月月换代，被框架绑死是最大的隐性成本。三条纪律：

  • 薄适配层：业务代码只依赖你自己定义的接口（LLM 调用、工具调用、记忆读写），框架实现沉到适配层，替换框架只改适配层。
  • 提示词与工具定義用数据不用框架对象：prompt 模板、工具 JSON Schema 存独立文件，不散落在框架 API 调用里。
  • 评测先行：50 条 eval case 用你自己的评测代码跑，这样任何框架都能被客观对比、随时替换。

Python 版本（LLM 适配层）

"""
LLM 适配层 —— Python
业务层只依赖 LLMClient 协议，底层换成 LangChain / 自研 / 任意框架都不动业务代码。
"""
from __future__ import annotations
from typing import Protocol, runtime_checkable

@runtime_checkable
class LLMClient(Protocol):
    """业务层唯一依赖的接口。"""
    def complete(self, system: str, user: str, **kw) -> str: ...

class OpenAICompatClient:
    """OpenAI 兼容实现（适配层之一，可替换为任意框架 SDK）。"""
    def __init__(self, base_url: str, api_key: str, model: str):
        from openai import OpenAI
        self._client = OpenAI(base_url=base_url, api_key=api_key)
        self._model = model

    def complete(self, system: str, user: str, **kw) -> str:
        r = self._client.chat.completions.create(
            model=self._model,
            messages=[{"role": "system", "content": system},
                      {"role": "user", "content": user}],
            temperature=kw.get("temperature", 0.3),
        )
        return r.choices[0].message.content or ""

# 业务代码只面向协议编程
def summarize(client: LLMClient, text: str) -> str:
    return client.complete("你是摘要助手", text[:4000])

if __name__ == "__main__":
    import os
    client = OpenAICompatClient(
        base_url=os.getenv("LLM_BASE_URL", "https://api.deepseek.com/v1"),
        api_key=os.environ["LLM_API_KEY"],
        model="deepseek-chat",
    )
    print(summarize(client, "（任意长文本）"))

TypeScript 版本（LLM 适配层）

/**
 * LLM 适配层 —— TypeScript
 */
interface LLMClient {
  complete(system: string, user: string, opts?: { temperature?: number }): Promise<string>;
}

export class OpenAICompatClient implements LLMClient {
  constructor(
    private baseUrl = process.env.LLM_BASE_URL ?? "https://api.deepseek.com/v1",
    private apiKey = process.env.LLM_API_KEY ?? "",
    private model = "deepseek-chat",
  ) {}

  async complete(system: string, user: string, opts?: { temperature?: number }) {
    const r = await fetch(`${this.baseUrl}/chat/completions`, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        Authorization: `Bearer ${this.apiKey}`,
      },
      body: JSON.stringify({
        model: this.model,
        messages: [
          { role: "system", content: system },
          { role: "user", content: user },
        ],
        temperature: opts?.temperature ?? 0.3,
      }),
    });
    const json = (await r.json()) as any;
    return json.choices[0].message.content ?? "";
  }
}

// 业务代码只依赖接口
async function summarize(client: LLMClient, text: string) {
  return client.complete("你是摘要助手", text.slice(0, 4000));
}

分阶段选型建议

  • MVP / 验证阶段（0–2 个月）：CrewAI 或 LangChain 快速出原型，目标是把场景跑通、把 eval 集建起来。
  • 生产化阶段（2–6 个月）：引入适配层把薄框架换厚或换薄，重点补可观测性（第 10 章）与安全网关（第 11 章）。
  • 规模化阶段（6 个月以上）：评估自研核心链路，框架只留边缘能力；工具与记忆按 MCP / 自有协议收敛（第 19 章）。

怎么看框架跑分

每个框架都会展示对自己有利的基准。阅读跑分时问五个问题，能过滤掉大部分噪音：

问题要防的偏差
跑的是哪个基准？什么版本的任务子集？挑选简单子集、自定义评测集
用什么模型？什么档位？用旗舰模型给自己贴金（框架能力 ≠ 模型能力）
重试几次取最好？pass@1 与 pass@k 混着报
计时从哪到哪？不含工具调用延迟的「裸模型时间」
对照组是谁？同期吗？和半年前的旧版本框架对比

结论：跑分用来建「候选短名单」（3 个以内），最终选型永远用你自己的 20 条 case 跑一遍。框架的 API 手感、调试体验、团队技术栈匹配度，权重高于任何公开跑分。

框架地图：三个档位，别混着比

市面上的 Agent 框架/平台看似有几十个，按「抽象层次」分只有三档。选型的第一步是想清楚自己在哪一档，跨档比较是选型最常见的时间浪费：

档位代表你在做什么什么时候选它
应用平台档（低代码）Coze / Dify / 阿里百炼画布上拖工作流，配知识库业务快速验证、无工程人力、接受平台约束
n8n / Zapier Agents连接 SaaS 做自动化编排流程以「连接现有系统」为主，智能成分低
AgentRadar 类平台面向运营的对话机器人纯对话场景，无复杂工具链
编排框架档（代码）LangGraph / CrewAI / AutoGen写代码组织多步流程与多 Agent要流程可控、要测试、要私有化部署
LlamaIndex / Haystack组织检索与数据管道核心是 RAG 而非复杂决策
Mastra / Vercel AI SDKTS 全栈的 Agent 编排团队是 Node 技术栈
厂商 SDK 档（托管）OpenAI Agents SDK / Claude Agent SDK用官方 SDK 调托管能力深度绑定单一厂商、要最快用上官方新特性
MCP 生态工具标准化工具供给工具要在多个 Agent/宿主间复用
开源 Agent 产品部署即用的完整产品通用需求（客服/问答）且不想开发

档位迁移策略：应用平台档验证价值 → 编排框架档接管核心流程 → 厂商 SDK 当补充能力。迁移时先固化「输入输出 schema」再换实现，这是第 13 章集成思路的具体应用。永远不要在低代码画布里实现核心算法——那不是平台的设计意图。
