第 3 章

记忆系统

分层设计、上下文管理、长期存储选型、记忆演化与多用户隔离

学习目标

  • 按认知科学模型设计记忆分层，并说出各层的存储选型依据
  • 掌握上下文工程四操作：Write / Select / Compress / Isolate
  • 判断何时从向量记忆升级到图记忆，何时用 Agentic RAG

章节地图：3.1 认知模型 → 3.2 短期记忆 → 3.3 长期记忆选型 → 3.4 演化 → 3.5 多用户隔离 → 3.6 上下文工程 → 3.7 图记忆 → 3.8 Agentic RAG → 本章产出。

3.1 记忆分层：工作记忆 / 情景记忆 / 语义记忆 / 程序记忆

受认知科学启发，Agent 记忆通常分为四层：

  • 工作记忆（Working Memory）：当前对话的上下文窗口，容量有限、易失。
  • 情景记忆（Episodic Memory）：「某月某日，用户问了 X，Agent 做了 Y」——具体事件的日志。
  • 语义记忆（Semantic Memory）：「用户喜欢简洁的回答」「项目 X 的数据库地址是 Y」——抽象出的稳定事实。
  • 程序记忆（Procedural Memory）：Agent 自己总结出的最佳实践、常用模板、工具调用模式。

3.2 短期上下文窗口的管理策略

LLM 的上下文窗口是有限资源。三种主流管理策略：

  • 滑动窗口（Sliding Window）：保留最近 N 条消息，丢弃更早的。实现简单，但会丢关键信息。
  • 压缩（Compression）：用 LLM 把旧消息总结成摘要，腾出空间。适合长对话。
  • 分层（Tiered）：最近的消息原样保留，较早的消息自动降级成摘要，更早的进长期记忆。

3.3 长期记忆的存储选型

存储类型优势劣势适用场景
向量库（Pinecone / Weaviate / pgvector）语义检索最自然精确查询弱、成本高非结构化知识、经验片段
结构化数据库（PostgreSQL）事务、索引、多租户成熟语义检索弱用户配置、任务状态、元数据
图数据库（Neo4j）关系推理强学习曲线陡实体关系、知识图谱
对象存储 + 元数据索引便宜、无限容量检索延迟高日志归档、审计记录

工程实践：多数场景用「pgvector（语义检索）+ PostgreSQL（结构化）」组合足够，不必一上来就上图数据库。

3.4 记忆演化：遗忘曲线、重要性评分、冲突消解

Agent 不能无限堆积记忆，需要主动管理：

  • 遗忘曲线：越久远的记忆权重越低，自然衰减。
  • 重要性评分：每次写入时由 LLM 或规则打分，低分记忆优先压缩或删除。
  • 冲突消解：当新旧记忆矛盾时（例如用户改了偏好），以最新且高分的记忆为准，旧记忆标记为过期而非删除。

3.5 多用户隔离

多租户 Agent 必须保证用户 A 看不到用户 B 的记忆。实现方式：

  • 会话级命名空间：每个 session 有唯一 ID，所有记忆读写都带 tenant_id + session_id 前缀。
  • 向量库过滤：pgvector 的元数据字段存 tenant_id，查询时加 WHERE 过滤。
  • 数据库行级安全（RLS）：PostgreSQL RLS 策略强制隔离，即使应用层出错也不串数据。

3.6 上下文工程：Write / Select / Compress / Isolate

记忆系统解决「存什么、怎么存」；上下文工程解决「每一轮决策时，往有限窗口里放什么」。模型窗口在扩大，但相关信息密度永远是稀缺资源——塞得越多，注意力越散，成本越高。上下文工程有四个标准操作：

操作要解决的问题常用手段
Write 写入中间结论不落盘，窗口滚动后就丢了scratchpad 便签、任务计划文件、结构化 notes
Select 选择窗口有限，记忆/工具/知识库全放进去不现实相关性检索、时间衰减、任务匹配度过滤
Compress 压缩长对话撑爆窗口且稀释注意力滚动摘要、历史折叠、关键事实抽取
Isolate 隔离多任务/多用户互相污染命名空间、会话级状态、子 Agent 上下文隔离

四操作与 3.1 的记忆分层是对偶关系：上下文是工作记忆的显式管理，记忆系统是它的持久化后端。实践中的预算分配经验：系统提示 + 工具定义占 10–20%，检索注入占 30–50%，近期对话占 20–30%，scratchpad 占 10%，始终预留 10% 余量给模型「思考」。

# Python：带 token 预算的上下文管理器（四操作的最小实现）
from dataclasses import dataclass, field

@dataclass
class ContextManager:
    budget: int = 4000                      # 上下文总 token 预算
    scratchpad: list[str] = field(default_factory=list)   # Write
    archive: list[str] = field(default_factory=list)      # 被压缩的历史

    def write(self, note: str):
        # 中间结论落盘，防滚动丢失
        self.scratchpad.append(note)

    def compress(self, history: list[str], keep_last: int = 4):
        # Compress：旧的折叠成摘要，只保留最近 N 条原文
        if len(history) <= keep_last:
            return history
        old, recent = history[:-keep_last], history[-keep_last:]
        self.archive.append("【摘要】" + "；".join(old))
        return recent

    def select(self, memories: list[str], query: str, top_k: int = 3):
        # Select：按相关度预算内取 Top-K（此处用词重叠率模拟）
        q = set(query)
        scored = sorted(memories, key=lambda m: -len(q & set(m)), reverse=False)
        return scored[:top_k]

    def build(self, query: str, memories: list[str], history: list[str]):
        # Isolate + 组装：按预算拼接，超预算先砍 scratchpad
        parts = ["【系统】你是任务助手。", "【问题】" + query]
        parts += ["【记忆】" + m for m in self.select(memories, query)]
        parts += ["【最近对话】" + h for h in self.compress(history)]
        parts += ["【便签】" + n for n in self.scratchpad[-3:]]
        ctx = "
".join(parts)
        while len(ctx) > self.budget and self.scratchpad:
            self.scratchpad.pop(0)          # 预算超限：先牺牲最旧的便签
            parts = parts[:-1] + ["【便签】" + n for n in self.scratchpad[-3:]]
            ctx = "
".join(parts)
        return ctx

// TypeScript：同样的四操作，带 token 预算控制
interface CtxOptions { budget: number }

class ContextManager {
  private budget: number;
  private scratchpad: string[] = [];
  private archive: string[] = [];

  constructor(opts: CtxOptions) { this.budget = opts.budget; }

  write(note: string) { this.scratchpad.push(note); }

  compress(history: string[], keepLast = 4): string[] {
    if (history.length <= keepLast) return history;
    const old = history.slice(0, -keepLast);
    this.archive.push("【摘要】" + old.join("；"));
    return history.slice(-keepLast);
  }

  select(memories: string[], query: string, topK = 3): string[] {
    const q = new Set(query);
    return [...memories]
      .sort((a, b) => (q.size - new Set([...q].filter(c => a.includes(c)).length)) -
                     (q.size - new Set([...q].filter(c => b.includes(c)).length))
    ).slice(0, topK);
  }

  build(query: string, memories: string[], history: string[]): string {
    const parts = ["【系统】你是任务助手。", "【问题】" + query];
    parts.push(...this.select(memories, query).map(m => "【记忆】" + m));
    parts.push(...this.compress(history).map(h => "【最近对话】" + h));
    parts.push(...this.scratchpad.slice(-3).map(n => "【便签】" + n));
    let ctx = parts.join("
");
    while (ctx.length > this.budget && this.scratchpad.length) {
      this.scratchpad.shift();
      ctx = parts.slice(0, -1)
        .concat(this.scratchpad.slice(-3).map(n => "【便签】" + n)).join("
");
    }
    return ctx;
  }
}

3.7 图记忆与知识图谱

向量检索擅长「语义相似」，但不擅长「关系推理」。当任务需要回答「A 的供应商的竞品有哪些」这类多跳问题时，把知识组织成图更自然。

维度向量记忆图记忆
擅长模糊语义匹配、文档问答多跳推理、关系约束、路径查询
写入成本低（切块 + embedding）高（实体抽取、关系对齐、消歧）
更新语义整块替换局部增删边，可追溯变更
典型场景客服知识库、文档助手企业关系网络、风控、研发依赖分析

落地节奏建议：先用向量跑通，把「关系查询失败」的 case 收集成评测集，再用图补这一块。混合形态（向量做粗排 + 图做精排/扩展）通常比纯图更稳。GraphRAG 的社区摘要技术适合「全局性问题」（如「这份财报的总体风险基调」），但构建成本高，中小规模数据不必上。

3.8 Agentic RAG：从被动检索到主动探索

朴素 RAG 是「用户问 → 检索 → 拼上下文 → 答」一次过；Agentic RAG 把检索本身变成 Agent 的一个工具，形成「查一步、想一步、再查一步」的循环。

  • 查询重写：多轮对话中把「它多少钱」改写成带主体的完整查询，解决指代消解。
  • 多跳检索：第一跳得到中间实体，用中间实体发起第二跳检索。
  • 检索后反思：评估检索结果是否支撑回答问题，不够就换关键词重查。
  • 引用与溯源：每个结论绑定来源片段，不可溯源的回答标为「低置信」。

代价是延迟和 token 成本随跳数增长。工程红线：检索跳数上限（通常 2–3 跳）+ 单问题检索次数配额，超限后降级为「基于现有信息回答 + 声明缺口」。

动手实验

  1. 打开你最近一次和 LLM 的长对话，数一数：如果窗口只保留最近 5 轮，会丢失哪些关键事实？这些就是应该 Write 进 scratchpad 的内容。
  2. 用 3.6 节的 ContextManager 跑一遍：故意把 budget 调到很小，观察便签被裁剪的顺序是否符合你的预期。
  3. 找 3 个你系统里需要「关系推理」的问题，判断它们值得上图记忆，还是用更好的 prompt 就能解决。

向量数据库选型：别急着上专用库

选向量库的第一原则：先看你的数据量级和团队技术栈，再看性能跑分。日写入十万级以下、又没有专职运维，PostgreSQL 的 pgvector 扩展或 Redis 的向量能力往往是综合成本最低的选择——你少维护一套系统。数据到千万级、QPS 要求高，再考虑专用向量库。

方案适用量级部署成本检索特性典型场景
pgvector（PostgreSQL）百万级以下极低（一个扩展）HNSW/IVFFlat，支持标量过滤混查已有 PG 的团队首选
Redis（向量 + 会话）百万级以下低内存级延迟，会话与向量同库高频小数据、需低延迟
Qdrant千万级中（Rust 单机/docker）标量过滤强，payload 过滤优秀过滤条件复杂的检索
Milvus亿级高（分布式组件多）多索引、多路召回、GPU 加速大规模生产检索
Elasticsearch千万级中向量 + 全文 BM25 混合检索原生支持已有 ES、要混排
Chroma原型/小规模极低（嵌入式）开箱即用，功能精简本地实验、Demo

混合检索是生产标配：纯向量检索会漏掉专有名词、编号、型号这类「精确匹配才靠谱」的查询。生产系统普遍采用「BM25 全文 + 向量语义」双路召回，再用 RRF（倒数排名融合）或重排模型合并结果——第 16 章的电商问数项目就是这么做的。只调一路向量的 RAG，在企业真实查询上通常漏召严重。

会话历史的工程细节：Redis 不是万能与不能

把对话历史丢进 Redis 是常见做法，但有三件事必须显式设计，否则线上一定出问题：

  • Key 设计与 TTL：chat:{tenant_id}:{session_id}，租户前缀保证多租户隔离；TTL 按业务设（客服场景常 7–30 天），别让历史无限堆积——它同时是成本和隐私负债。
  • 序列化格式：存结构化消息数组（role/content/tool_calls 完整保留），不要存拼好的 prompt 字符串——否则后续压缩、裁剪、统计都没法做。
  • 滑动窗口 + 摘要的两级策略：Redis 里只保留最近 N 条原文，更早的滚动压缩成一段摘要（第 5 章上下文工程的 Compress 操作）。窗口大小 N 和模型上下文预算联动，N 不是拍脑袋定的。
# 两级历史：Redis 原文窗口 + 滚动摘要（伪代码，替换为你的 redis 客户端）
import json, redis

r = redis.Redis(host='localhost', port=6379)

def key(sid): return 'chat:%s' % sid

def append_turn(sid, role, content):
    msg = json.dumps({'role': role, 'content': content}, ensure_ascii=False)
    r.rpush(key(sid), msg)
    r.expire(key(sid), 7 * 86400)
    # 超过 40 条时，把最旧的 20 条滚动进摘要，只保留最近 20 条原文
    if r.llen(key(sid)) > 40:
        old = [json.loads(m) for m in r.lrange(key(sid), 0, 19)]
        summary = summarize(old)  # 调用 LLM 压缩
        r.delete(key(sid))
        r.rpush(key(sid), json.dumps({'role': 'system', 'content': '前情摘要：' + summary}, ensure_ascii=False))
        for m in r.lrange(key(sid) + ':tmp', 20, -1):
            r.rpush(key(sid), m)
        r.delete(key(sid) + ':tmp')

import Redis from 'ioredis';
const r = new Redis();

const key = (sid: string) => `chat:${sid}`;

async function appendTurn(sid: string, role: string, content: string) {
  await r.rpush(key(sid), JSON.stringify({ role, content }));
  await r.expire(key(sid), 7 * 86400);
  if ((await r.llen(key(sid))) > 40) {
    // 取出最旧 20 条 → 摘要 → 重建列表（摘要 + 最近 20 条原文）
    const old = (await r.lrange(key(sid), 0, 19)).map((m) => JSON.parse(m));
    const summary = await summarize(old);
    const recent = await r.lrange(key(sid), 20, -1);
    await r.del(key(sid));
    await r.rpush(key(sid), JSON.stringify({ role: 'system', content: `前情摘要：${summary}` }));
    if (recent.length) await r.rpush(key(sid), ...recent);
  }
}

注意这两个示例省略了并发写保护的细节（多轮并发时 Lua 脚本或分布式锁），生产实现请把「读出旧条 → 算摘要 → 重建列表」做成原子操作。

本章产出：最小双层记忆实现

一个同时具备「短期上下文 + 长期向量检索」的记忆模块。

Python 版本

"""
双层记忆：会话上下文（short）+ 向量检索（long）
依赖：openai >= 1.0（用于 embedding）
"""
from __future__ import annotations
from dataclasses import dataclass, field
from typing import List
import openai

client = openai.OpenAI()

@dataclass
class MemoryItem:
    text: str
    embedding: List[float] = field(default_factory=list)
    score: float = 1.0  # 重要性，0–1

class ShortTermMemory:
    """滑动窗口：只保留最近 N 条"""
    def __init__(self, capacity: int = 20):
        self.capacity = capacity
        self.items: List[str] = []

    def add(self, text: str):
        self.items.append(text)
        if len(self.items) > self.capacity:
            self.items.pop(0)

    def get_context(self) -> str:
        return "\n".join(self.items)

class LongTermMemory:
    """简化向量记忆：用 OpenAI embedding + 内嵌暴力检索"""
    def __init__(self):
        self.store: List[MemoryItem] = []

    def _embed(self, text: str) -> List[float]:
        r = client.embeddings.create(model="text-embedding-3-small", input=text)
        return r.data[0].embedding

    def add(self, text: str, score: float = 1.0):
        item = MemoryItem(text=text, embedding=self._embed(text), score=score)
        self.store.append(item)

    def search(self, query: str, top_k: int = 3) -> List[str]:
        q_vec = self._embed(query)
        scored = []
        for item in self.store:
            sim = sum(a * b for a, b in zip(q_vec, item.embedding))
            scored.append((sim * item.score, item.text))
        scored.sort(reverse=True)
        return [t for _, t in scored[:top_k]]

# 使用示例
mem = LongTermMemory()
mem.add("用户偏好简洁回答", score=0.9)
mem.add("项目数据库地址是 10.0.0.5", score=0.8)
print(mem.search("项目数据库"))  # → ["项目数据库地址是 10.0.0.5", ...]

  constructor(private capacity = 20) {}
  add(text: string) {
    this.items.push(text);
    if (this.items.length > this.capacity) this.items.shift();
  }
  getContext() { return this.items.join("\n"); }
}

class LongTermMemory {
  private store: MemoryItem[] = [];
  constructor(private client: OpenAI) {}

  private async embed(text: string): Promise {
    const r = await client.embeddings.create({ model: "text-embedding-3-small", input: text });
    return r.data[0].embedding;
  }

  async add(text: string, score = 1.0) {
    const embedding = await this.embed(text);
    this.store.push({ text, embedding, score });
  }

  async search(query: string, topK = 3): Promise {
    const qVec = await this.embed(query);
    const scored = this.store.map(item => ({
      sim: qVec.reduce((s, a, i) => s + a * item.embedding[i], 0) * item.score,
      text: item.text,
    }));
    scored.sort((a, b) => b.sim - a.sim);
    return scored.slice(0, topK).map(s => s.text);
  }
}

// 使用示例
(async () => {
  const mem = new LongTermMemory(new OpenAI());
  mem.store = [
    { text: "用户偏好简洁回答", embedding: [], score: 0.9 },
    { text: "项目数据库地址是 10.0.0.5", embedding: [], score: 0.8 },
  ];
  // 生产环境应先调用 add() 写入 embedding
  console.log(await mem.search("项目数据库"));
})();
