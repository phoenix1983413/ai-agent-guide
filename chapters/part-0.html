Part 0

为什么需要了解 Agent

面向产品经理、技术负责人与决策者

Agent 不是下一个 Chatbot

过去两年，绝大多数组织对「AI 能力」的想象停留在问答、摘要、翻译。大模型把这些事情做到了可用，但真正拉开差距的是让 AI 自主行动——读取数据、调用工具、修改系统、等待反馈、再调整策略。

这就是 Agent 的本质：一个能感知环境、制定计划、执行动作、观察结果并自我修正的闭环系统。判断一个项目是不是 Agent 项目，只看一件事：它有没有「行动闭环」。只有对话没有行动，是 Chatbot；有行动、能根据结果调整下一步，才是 Agent。

Agent 能力光谱：先判断你处在哪一级

不同「自主程度」的 Agent，工程复杂度、成本、风险完全不同。立项前先对号入座：

等级能力典型形态工程复杂度风险
L1 工具调用单步：识别意图 → 调一个工具 → 返回智能客服单轮查询、表单填写助手低低
L2 任务规划多步：拆解任务、按序执行、失败重试数据分析助手、调研报告生成中中
L3 多 Agent 协作多角色分工、互相评审、长时运行研发团队 Agent、自动化运营高高

建议：第一个项目永远从 L1 起步，验证稳定后再上 L2，L3 等前三章技术债还清再说。跳级是 Agent 项目失败的头号原因。

Agent 能解决什么问题

  • 把「人脑里的操作手册」变成自动化流程：查数 → 制表 → 发邮件，过去需要人串联的工具，现在 Agent 串联。
  • 在长链条任务里保持上下文：多步骤、跨系统、需要中间判断的任务，Chatbot 会忘，Agent 有记忆。
  • 7×24 值守，但只在必要时打扰人：监控、巡检、异常报警，Agent 可以一直跑，出事才找你。
  • 把专家经验沉淀成可复用策略：高级工程师的排查思路、客服的应对流程，都可以编码成 Agent 策略。

Agent 不能解决什么问题

  • 没有明确目标的任务：「帮我搞搞那个数据」——模糊输入只能得到随机输出。目标定义能力是决策者的活，不是模型的活。
  • 没有稳定工具层的系统：Agent 需要可调用的 API、可读的数据库、可写的工单系统。工具越规范，Agent 越可靠；系统本身烂，Agent 只是烂得快。
  • 没有权限模型的场景：Agent 权限最小化是必修课。连「谁能干什么」都说不清的系统，上 Agent 等于发免罪金牌。
  • 幻觉风险零容忍的场景：医疗诊断、司法认定、金融风控——在这些领域，Agent 目前只能是「辅助」，不能是「执行」。

值不值得做：一页 ROI 账

决策者最该问的问题不是「Agent 强不强」，而是「这账算得过」。算三笔账：

  1. 人力账：任务当前占用多少人工工时？Agent 能替代多少比例？（经验值：规则清晰的重复流程可替代 60–80%，需要判断的可替代 20–40%。）
  2. 成本账：模型调用费用 + 工程投入摊销。下面的成本测算器可以直接套用：输入月查询量、平均 token 数、单价，一分钟算出月度 API 成本。
  3. 风险账：错误一次的最大损失 × 月度错误次数。如果单次错误的损失不可承受（如误退款、误删除），先补权限与人工确认机制，再谈效率。

Python 版本

"""
Agent ROI 成本测算器 —— Python
输入业务量，输出月度 API 成本与「回本月数」，用于立项前估算。
"""
from __future__ import annotations
from dataclasses import dataclass

# 粗略经验值：一次带工具调用的 Agent 任务 ≈ 3 轮对话
AVG_INPUT_TOKENS, AVG_OUTPUT_TOKENS, TURNS = 2000, 600, 3

@dataclass
class CostInput:
    monthly_tasks: int              # 月任务量
    price_in_per_m: float           # 输入单价（元 / 百万 token）
    price_out_per_m: float          # 输出单价
    build_cost: float               # 一次性工程投入（元）
    labor_saved_per_task: float     # 每个任务节省的人力成本（元）

def estimate(c: CostInput) -> dict:
    tokens_in = c.monthly_tasks * AVG_INPUT_TOKENS * TURNS
    tokens_out = c.monthly_tasks * AVG_OUTPUT_TOKENS * TURNS
    api_cost = (tokens_in / 1e6 * c.price_in_per_m
                + tokens_out / 1e6 * c.price_out_per_m)
    labor_saved = c.monthly_tasks * c.labor_saved_per_task
    net_gain = labor_saved - api_cost
    payback = (c.build_cost / net_gain) if net_gain > 0 else float("inf")
    return {
        "月度 API 成本（元）": round(api_cost, 2),
        "月度节省人力（元）": round(labor_saved, 2),
        "月度净收益（元）": round(net_gain, 2),
        "回本月数": "永不" if payback == float("inf") else round(payback, 1),
    }

if __name__ == "__main__":
    # 示例：每月 2 万次查询，中端模型，每单省 3 分钟人力
    scenario = CostInput(
        monthly_tasks=20_000,
        price_in_per_m=2.0,          # 元 / 百万输入 token
        price_out_per_m=8.0,         # 元 / 百万输出 token
        build_cost=150_000,          # 工程投入 15 万
        labor_saved_per_task=1.5,    # 每任务省 1.5 元人力
    )
    for k, v in estimate(scenario).items():
        print(f"{k}: {v}")

/**
 * Agent ROI 成本测算器 —— TypeScript
 */
interface CostInput {
  monthlyTasks: number;
  priceInPerM: number;          // 元 / 百万输入 token
  priceOutPerM: number;         // 元 / 百万输出 token
  buildCost: number;
  laborSavedPerTask: number;    // 元 / 任务
}

const AVG_INPUT_TOKENS = 2000;
const AVG_OUTPUT_TOKENS = 600;
const TURNS = 3;

export function estimate(c: CostInput) {
  const tokensIn = c.monthlyTasks * AVG_INPUT_TOKENS * TURNS;
  const tokensOut = c.monthlyTasks * AVG_OUTPUT_TOKENS * TURNS;
  const apiCost = tokensIn / 1e6 * c.priceInPerM
                + tokensOut / 1e6 * c.priceOutPerM;
  const laborSaved = c.monthlyTasks * c.laborSavedPerTask;
  const netGain = laborSaved - apiCost;
  return {
    "月度 API 成本（元）": Number(apiCost.toFixed(2)),
    "月度节省人力（元）": Number(laborSaved.toFixed(2)),
    "月度净收益（元）": Number(netGain.toFixed(2)),
    "回本月数": netGain > 0 ? Number((c.buildCost / netGain).toFixed(1)) : "永不",
  };
}

三类团队，三种起步方式

团队类型推荐起步预计见到价值的时间关键风险
有研发能力的团队从第 1 章的最小 Agent 开始，1–2 周内内部跑通一个原型2–4 周过度设计，一上来就搭多 Agent
有业务场景但缺工程资源先用 CrewAI / AutoGen 等框架搭 demo，验证 ROI 后再投入自研1–3 个月被框架绑死，后期迁移成本高
纯决策层读 Part 0 + 第 1 章建立判断力，重点看能力光谱与三种起步方式1 天把 demo 效果当生产效果

立项前 checklist

  • □ 目标场景能用一句话说清，且能量化（任务数、耗时、错误率）
  • □ 有至少一个可调用、可测试的工具层（API / 数据库 / 文档）
  • □ 权限模型已定义：谁能做什么、危险操作谁批准
  • □ ROI 测算过：净收益为正，回本周期可接受
  • □ 有 eval 集计划：上线前先建 50 条测试用例
  • □ 有回滚预案：Agent 关闭后业务能退回原流程

Agent 还是自动化：先回答三个问题

大量「Agent 项目」失败的第一原因，是任务本身不需要 Agent。立项前先用下面三问做最简形态匹配：

问题偏向工作流（Workflow / 自动化）偏向 Agent
执行路径是否预先可知？步骤固定、分支有限，人工能直接画成流程图路径依赖中间结果，无法在写代码时枚举
犯错的代价是什么？错了会造成资金、安全、合规损失 → 必须固定流程 + 人工审批错了可撤销、可重试，人工逐单复核的成本更高
任务出现频率如何？每天成千上万次的重复任务，规则引擎更便宜、更稳定长尾、低频、每次的形态都不一样

三问里只要有任意一问偏向工作流，就先用工作流实现；确实需要动态决策的那一小段，再单独包一层小 Agent。最简形态原则：能用 if/else 解决的不要调模型；能一次调用解决的不要循环；能用循环解决的不要上多 Agent。

能力认知层级：你的团队在第几级

「分层能力模型」（第 1 章）从功能视角看 Agent；这一张表从自主度视角看，方便评估团队现状与目标：

层级能力描述工程形态人的角色
L1 反射式固定输入触发固定动作，无内部状态规则引擎、脚本、Webhook编写规则
L2 目标驱动给定目标，按预定义流程执行，可处理简单分支Workflow / DAG 编排设计流程
L3 规划执行自行拆解任务、调用工具、按结果调整计划ReAct / Plan-and-Execute 单 Agent定义目标与边界
L4 反思进化评估自身输出、从失败中修正、积累可复用经验Reflexion 循环 + 记忆库设定红线与验收
L5 多智能体多个角色分工协作，动态组队与仲裁Multi-Agent 编排设计组织与治理

绝大多数企业的现实起点是 L1–L2：把最耗时、最重复的 20% 环节自动化，往往就能拿到 80% 的收益。直接跳 L4/L5 的项目，失败率显著更高。

什么时候不要上 Agent

  • 答案要求 100% 确定且可解释：财务核算、合规判定、医疗诊断建议——用确定性系统，Agent 只做辅助检索。
  • 数据是核心机密且无法脱敏：先把 PII 过滤和租户隔离（第 11 章）做好，再谈智能。
  • 没有评测集：连「什么样算对」都说不清，就无法判断 Agent 是在帮忙还是在添乱（第 9 章）。
  • 高频简单任务：每天百万次的分类/抽取，微调小模型或规则更经济。

本章小结

Agent 是「能自主行动的 AI」，不是 Chatbot 的升级版，而是一个新品类。它的价值在多步骤、跨系统、需要持续观察和调整的任务里最明显。落地的前提是：有明确场景、有可调用工具、有权限模型、有灰度机制。把这四条和上面的 checklist 对着过一遍，你就可以立项了。
