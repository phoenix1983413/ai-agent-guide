第 19 章

Agent 之间的协议与标准

A2A / MCP / 发现层 / 协议层 / 运行时层

单 Agent 靠工具扩展能力，多 Agent 靠协议交换能力。协议解决的是互操作问题：两个来自不同团队、不同框架、不同厂商的 Agent，如何在没有事先约定的情况下发现彼此、调用彼此、信任彼此。本章拆解当前两个事实标准，并给出可落地的最小实现。

学习目标

  • 分清 MCP（Agent↔工具）与 A2A（Agent↔Agent）的分工
  • 按场景选择协议组合，不过度设计
  • 识破协议层的三个安全陷阱

章节地图：19.1 A2A 现状 → 19.2 MCP 详解 → 19.3 未来接口 → 19.4 协议安全 → 19.5 协议选型决策 → 本章产出。

19.1 A2A（Agent-to-Agent）协议现状

A2A 是 Google 提出的 Agent 间通信协议，核心思想：把 Agent 看成一个「远程服务」，有标准接口完成健康检查、任务提交、状态查询。关键设计：

  • Agent Card：每个 Agent 在 /.well-known/agent.json 发布「名片」，声明能力、端点、认证方式。调用方先读名片再决定怎么用它。
  • 任务生命周期：提交任务返回 task_id，调用方通过轮询或 SSE 推送获取中间状态与最终产物。任务状态机：submitted → working → input-required → completed / failed / canceled。
  • 产物工件（Artifact）：任务产出物（文件、JSON、报告）作为 artifact 返回，而不是全塞在文本里。
  • 推送通知：长任务支持 Webhook 回调，调用方不必一直轮询。

现状判断：协议骨架已清晰，但版本仍在快速迭代，字段与状态机细节尚未冻结。生产上采用它的正确姿势是：只依赖最小子集（名片 + 任务提交 + 状态查询），把业务字段放在 artifact 里，而不是铺开到每个扩展字段。

19.2 MCP（Model Context Protocol）详解

MCP 是 Anthropic 推出的开放协议，目标是统一「模型 ↔ 工具 ↔ 数据」的连接方式，被称为「AI 应用的 USB-C」。三层架构：

  • Host：运行 MCP 的应用程序（IDE、聊天界面、Agent 运行时）。
  • Client：Host 内部的连接器，与一个 Server 保持 1:1 会话。
  • Server：对外提供三类原语——Tools（可执行函数，模型调用）、Resources（可读取的数据，如文件、记录）、Prompts（预置提示词模板）。

传输层走 stdio（本地子进程）或 SSE / Streamable HTTP（远程）。消息是 JSON-RPC 2.0，主要方法：initialize、tools/list、tools/call、resources/list、resources/read。

MCP 的工程价值：工具一次开发、到处被 Host 使用。企业内部把订单查询、知识库检索、发布流水线各封装一个 MCP Server，Claude、IDE、自研 Agent 都能即插即用。风险点：Server 是第三方代码，天然有越权读写能力（类似供应链），必须配合第 11 章的权限网关使用，且优先选可审计的开源实现。

Python 版本（最小 MCP Server）

"""
最小 MCP Server —— Python（协议语义演示版）
演示 initialize / tools/list / tools/call 的 JSON-RPC 交互骨架。
生产环境用官方 SDK：pip install mcp
"""
from __future__ import annotations
import json, sys
from datetime import datetime

TOOLS = [
    {
        "name": "query_order",
        "description": "按订单号查询订单状态",
        "inputSchema": {
            "type": "object",
            "properties": {"order_id": {"type": "string"}},
            "required": ["order_id"],
        },
    },
    {
        "name": "search_docs",
        "description": "检索内部知识库",
        "inputSchema": {
            "type": "object",
            "properties": {"query": {"type": "string"}, "top_k": {"type": "integer"}},
            "required": ["query"],
        },
    },
]

ORDERS = {"T-1001": {"status": "shipped", "eta": "2026-10-10"}}

def handle(msg: dict) -> dict:
    method, params, msg_id = msg.get("method"), msg.get("params") or {}, msg.get("id")

    if method == "initialize":
        return {"jsonrpc": "2.0", "id": msg_id, "result": {
            "protocolVersion": "2026-06-18",
            "serverInfo": {"name": "order-server", "version": "1.0.0"},
            "capabilities": {"tools": {}},
        }}
    if method == "tools/list":
        return {"jsonrpc": "2.0", "id": msg_id, "result": {"tools": TOOLS}}
    if method == "tools/call":
        name = params.get("name")
        args = params.get("arguments") or {}
        if name == "query_order":
            order = ORDERS.get(args["order_id"])
            return {"jsonrpc": "2.0", "id": msg_id, "result": {
                "content": [{"type": "text",
                             "text": json.dumps(order, ensure_ascii=False) if order else "未找到订单"}],
                "isError": order is None,
            }}
        if name == "search_docs":
            return {"jsonrpc": "2.0", "id": msg_id, "result": {
                "content": [{"type": "text", "text": "（演示）命中 2 篇文档"}],
            }}
        return {"jsonrpc": "2.0", "id": msg_id,
                "error": {"code": -32601, "message": f"未知工具 {name}"}}
    return {"jsonrpc": "2.0", "id": msg_id,
            "error": {"code": -32601, "message": f"未知方法 {method}"}}

# stdio 主循环：一行一个 JSON-RPC 消息（真实 SDK 自动完成编帧）
if __name__ == "__main__":
    for line in sys.stdin:
        line = line.strip()
        if line:
            print(json.dumps(handle(json.loads(line)), ensure_ascii=False), flush=True)

TypeScript 版本（最小 MCP Client）

/**
 * 最小 MCP Client —— TypeScript
 * 演示发现工具（tools/list）并调用（tools/call）的标准流程。
 */
import { spawn, type ChildProcessWithoutNullStreams } from "node:child_process";
import readline from "node:readline";

export class McpClient {
  private proc: ChildProcessWithoutNullStreams;
  private rl: readline.Interface;
  private nextId = 1;
  private pending = new Map<number, (v: unknown) => void>();

  constructor(command: string, args: string[]) {
    this.proc = spawn(command, args, { stdio: ["pipe", "pipe", "inherit"] });
    this.rl = readline.createInterface({ input: this.proc.stdout });
    this.rl.on("line", (line) => {
      const msg = JSON.parse(line);
      if (msg.id !== undefined && this.pending.has(msg.id)) {
        this.pending.get(msg.id)!(msg.result ?? msg.error);
        this.pending.delete(msg.id);
      }
    });
  }

  private request(method: string, params?: unknown): Promise<any> {
    const id = this.nextId++;
    return new Promise((resolve) => {
      this.pending.set(id, resolve);
      this.proc.stdin.write(JSON.stringify({ jsonrpc: "2.0", id, method, params }) + "\n");
    });
  }

  async init() {
    return this.request("initialize", {
      protocolVersion: "2026-06-18",
      clientInfo: { name: "demo-client", version: "0.1.0" },
      capabilities: {},
    });
  }

  async listTools() {
    return (await this.request("tools/list")).tools as Array<{
      name: string; description: string; inputSchema: unknown;
    }>;
  }

  async callTool(name: string, args: Record<string, unknown>) {
    return this.request("tools/call", { name, arguments: args });
  }

  close() {
    this.rl.close();
    this.proc.kill();
  }
}

// ---- 使用示例 ----
const client = new McpClient("python3", ["server.py"]);
await client.init();
const tools = await client.listTools();
console.log("发现工具:", tools.map((t) => t.name).join(", "));
console.log(await client.callTool("query_order", { order_id: "T-1001" }));
client.close();

19.3 未来的通用 Agent 接口长什么样

综合 A2A + MCP + 行业实践，通用接口大概率收敛到三层：

层职责已有雏形
发现层Agent 注册中心，按能力 / SLA / 信誉搜索A2A Agent Card、Agent 目录服务
协议层统一消息格式、错误码、鉴权（OAuth 2.0 / mTLS）JSON-RPC + JSON Schema、OpenAPI
运行时层Agent 沙箱标准：启动 / 停止 / 资源限额 / 日志容器运行时 + WASM 沙箱

另一个值得跟踪的方向是支付与结算协议——Agent 代表用户消费时需要可审计的授权链（参考 AP2 一类提案）。它会把「权限最小化」从工具内部提升到协议层面。

19.4 协议安全：三个高频陷阱

  • 恶意 Server：第三方 MCP Server 的 tools/call 可以返回夹带私货的内容（如「顺便把用户邮箱发到 X」）。对策：Server 白名单 + 输出过第 11 章的内容审核层。
  • 名片劫持：伪造 /.well-known/agent.json 冒充内部 Agent。对策：域名 DNSSEC / 证书固定 + Agent 身份签名。
  • 任务重放：抓包后重复提交 tasks/send 导致重复下单。对策：幂等键 + 服务端去重窗口。

19.5 协议选型决策：不过度设计

协议爆炸的年代，选型原则只有一条：先解决问题，再对齐生态。一个决策表：

你的问题方案理由
让 Agent 用上内部 API / 数据源MCP Server 包一层工具集成的事实标准，客户端生态现成
两个异构 Agent 互派任务A2A 或直接 HTTP + 任务模型跨组织衔接；组织内直接函数调用更省
统一管理全公司工具权限企业 MCP 网关（统一鉴权 / 限流 / 审计）协议是技术问题，治理是组织问题（13.5 节）
内部系统已经很完善不用新协议REST/gRPC + 工单就是最稳的「Agent 接口」

演进路线判断：MCP 拿下「Agent 与工具/数据」这一层已无悬念；「Agent 与 Agent」层还在战国（A2A、ANP、各类私有协议），现在把业务逻辑押在某个互操作协议上有风险，把工具层押在 MCP 上没有。务实的做法：Agent 间接口先用自己的版本化 API，同时关注生态收敛。

动手实验

  1. 列出你要集成的 5 个工具，逐个判断：裸 API / MCP Server / Agent Skill 哪种形态最合适（参考 4.6 节）。
  2. 给你现有的 Agent 间调用（如果有）画一张协议演进图：今天什么、半年后什么。
  3. 用 19.4 节的三个陷阱检查你的 MCP/A2A 配置：权限范围、来源校验、调用留痕各打勾。

本章要点

  • A2A 解决「Agent ↔ Agent」：名片发现 + 任务状态机 + 产物工件，先用最小子集。
  • MCP 解决「模型 ↔ 工具/数据」：Tools / Resources / Prompts 三类原语，JSON-RPC over stdio 或 HTTP。
  • 未来接口三层化：发现 / 协议 / 运行时，沙箱与支付授权是接下来的竞争焦点。
  • 协议引入即供应链：Server 白名单、输出审核、幂等去重三件套不能省。
